این سه تا چی هستن؟ الگوی معماری، نه محصول

دیتاورهاوس، دیتالیک و لیک‌هاوس سه جواب متفاوت به یک سؤال‌ان: دادهٔ تحلیلی سازمان رو کجا، به چه شکلی و با چه قواعدی نگه داریم تا همه بتونن روش تحلیل کنن؟
محصول‌ها پیاده‌سازیشون می‌کنن:Snowflake · BigQuery ← ورهاوسS3 + Spark ← لیکIceberg + Trino ← لیک‌هاوس
هر معماری یعنی یک جواب به این پنج سؤال:
۱محل ذخیرهدیسک خود دیتابیس، یا Object Storage ارزون (S3، MinIO)؟
۲فرمت دادهفرمت داخلی و بسته، یا فایل باز مثل Parquet؟
۳متادیتا و جدولچه کسی می‌دونه «جدول» چیه، اسکیماش چیه و کدوم فایل‌ها مال اونه؟
۴موتور پردازشیک موتور یکپارچه، یا چند موتور جدا (Spark، Trino، ClickHouse)؟
۵قواعداسکیما موقع نوشتن چک بشه یا موقع خوندن؟ کیفیت و دسترسی رو کی کنترل کنه؟
نکتهٔ کلیدی: این‌ها نوع دیتابیس نیستن؛ یک پله بالاترن. «نوع دیتابیس» یعنی یک موتور؛ «معماری» یعنی کنار هم چیدن ذخیره، فرمت، متادیتا، موتور و قواعد. این پنج سؤال ستون‌های جدول مقایسهٔ آخر جلسه هم هستن.

Fact: رویدادی که اتفاق افتاده و قابل اندازه‌گیریه؛ هر ردیف یک قلم خرید. عددهاش (amount، quantity) اسمشون سنجه (Measure) است.
Dimension: زمینهٔ رویداد؛ چه کسی، کِی، چی، کجا. ستون‌هاش ویژگی‌ان: اسم، دسته‌بندی، ماه، استان.
دانه‌بندی (Grain): اولین تصمیم: «هر ردیف Fact دقیقاً چیه؟» یک سفارش، یا یک کالا در سفارش؟

ستاره‌ای، دانه‌برفی، و مدل OLTP

⭐ ستاره‌ای (Star)

fact_sales ── dim_customer (name, city, province)

بُعدها دی‌نرمال‌ان؛ شهر و استان داخل همون dim_customer. کوئری ساده و سریع. رایج‌ترین در ورهاوس.

❄ دانه‌برفی (Snowflake)

fact_sales ── dim_customer └─ dim_city ─ dim_province

بُعدها خودشون نرمال‌ان؛ تکرار کمتر، ولی join بیشتر و کوئری پیچیده‌تر.

⚙ مدل OLTP (3NF)

orders ─ order_items ─ products └ customers ─ addresses ─ cities

برای ثبت بدون تکرار طراحی شده؛ برای تحلیل، ده‌ها join لازم داره.

SELECT c.city, d.month, SUM(f.amount) FROM fact_sales f JOIN dim_customer c USING (customer_key) JOIN dim_date d USING (date_key) GROUP BY c.city, d.month;
با مدل ستاره‌ای «فروش هر شهر در هر ماه» فقط دو join ساده است. OLTP برای نوشتن طراحی شده؛ ورهاوس برای خوندن.
ارتباط با جلسهٔ قبل: OLTP نرمال برای نوشتن بدون تکرار؛ OLAP دی‌نرمال برای خوندن ساده. موتورهای ستونی تکرار رو با فشرده‌سازی جبران می‌کنن، پس دی‌نرمال بودن گرون نیست.

دو مکتب طراحی: Inmon و Kimball

Inmon · از بالا به پایین

منابع→انبار مرکزی نرمال (3NF)→Martهای ستاره‌ای

اول یک انبار سازمانی کامل و نرمال؛ بعد برای هر تیم یک Mart. یکپارچه و دقیق، ولی کند و پرهزینه برای شروع.

Kimball · از پایین به بالا

خوندن: هر تیم، اسکیمای خودش

تیم فروش

اسکیما موقع کوئری تعریف می‌شه؛ هر خواننده داده رو یک‌جور تفسیر می‌کنه.

SQL روی پوشه‌ها؟ Hive Metastore

Metastore: جدول = پوشه + اسکیما

tablelocationschema
clickss3://lake/raw/clicks/user, page, price
orderss3://lake/raw/orders/id, city, amount
پارتیشن یعنی زیرپوشه؛ پس WHERE date = '2026-08-02' فقط یک پوشه رو می‌خونه (Partition Pruning). همون ایدهٔ «پرش» جلسهٔ قبل، این بار در سطح پوشه.
محدودیت کلیدی: Metastore فقط می‌دونه کدوم پوشه مال جدوله؛ نه کدوم فایل‌ها معتبرن و نه کدوم نسخه. هر فایلی توی پوشه باشه، جزو جدول حساب می‌شه. (این نکته کلید لیک‌هاوسه.)
s3://lake/raw/clicks/ ├── date=2026-08-01/ │ ├── part-0001.json │ └── part-0002.json ├── date=2026-08-02/ ← WHERE date=… │ ├── part-0001.json │ └── part-0002.json └── date=2026-08-03/ └── part-0001.json
Hive Metastore از دنیای Hadoop اومد و هنوز همه‌جا هست (Spark و Trino ازش استفاده می‌کنن). «جدول» یک مفهوم منطقیه که روی پوشه‌ها سوار شده.

کلید ۳ اشاره‌گر رو جابه‌جا می‌کنه. این همون A در ACID است، بدون اینکه Object Storage خودش تراکنش داشته باشه؛ فقط Catalog باید یک «compare-and-swap» اتمیک داشته باشه.

HDFS در برابر Object Storage: چرا S3 برنده شد؟

HDFS (Hadoop)

  • فایل‌سیستم توزیع‌شده روی دیسک سرورهای خودمون
  • ذخیره و پردازش روی همون سرورها (data locality)
  • NameNode متادیتای همهٔ فایل‌ها رو در حافظه نگه می‌داره ← فایل کوچیک زیاد = دردسر
  • برای بیشتر کردن فضا باید سرور (با CPU) خرید
  • نگهداری سنگین (تیم Hadoop)

Object Storage (S3، MinIO)

  • ذخیرهٔ «شیء» با کلید، روی HTTP؛ تقریباً بی‌انتها
  • ذخیره کاملاً جدا از پردازش؛ هر کدوم جدا بزرگ می‌شه
  • بسیار ارزون و بادوام (۱۱ تا ۹)
  • بدون rename و append واقعی؛ آپدیت درجا نداره
  • MinIO و Ceph: همین API روی سرورهای خودمون (on-premise)
جداسازی ذخیره از پردازش و هزینهٔ کم، Object Storage رو پایهٔ دیتالیک و لیک‌هاوس امروزی کرد. نبود آپدیت درجا هم یکی از دلایلیه که Table Format لازم شد.

Copy-on-Write در برابر Merge-on-Read

Copy-on-Write

موقع حذف یا آپدیت، هر فایلی که ردیف تغییرکرده داره کامل دوباره نوشته می‌شه.
✓ خوندن ساده و سریع؛ فقط فایل‌های معمولی.
✕ نوشتن گرون؛ آپدیت یک ردیف در فایل ۲۵۶ مگی یعنی نوشتن ۲۵۶ مگ.
مناسب: آپدیت کم، خوندن زیاد (گزارش‌ها).

Merge-on-Read

فقط یک فایل کوچیک delete file نوشته می‌شه (موقعیت یا مقدار ردیف‌های حذف‌شده)؛ خواننده موقع خوندن اعمالش می‌کنه؛ Compaction بعداً ادغامشون می‌کنه.
✓ نوشتن سریع؛ مناسب CDC و استریم.
✕ خوندن کمی کُندتر تا قبل از Compaction.
دقیقاً ایدهٔ LSM: الان یادداشت، بعداً ادغام.

Compaction

Expire Snapshots

CALL system.expire_snapshots('shop.orders', TIMESTAMP '2026-07-01');

۱. ستون جدید اضافه شده

ستون‌ها با اسم انتخاب شده باشن ← چیزی نمی‌شکنه، فقط از دادهٔ جدید بی‌خبریم. SELECT * زده باشیم ← job ساعت ۳ صبح می‌خوابه.

۲. ستون حذف یا اسمش عوض شده

خطای column does not exist؛ pipeline متوقف می‌شه. بده، ولی حداقل زود می‌فهمیم.

۳. نوع ستون عوض شده

گاهی خطای تبدیل، گاهی بی‌صدا یه جای دیگه رو خراب می‌کنه (مثلاً مرتب‌سازی متنی به‌جای عددی).

تومان شد ریال، یا وضعیت جدید «مرجوعی» اومد. هیچ خطایی نمی‌ده، همه‌چیز سبزه، ولی عددهای گزارش غلطه.

LSM-Tree: اول سریع بنویس، بعداً مرتب کن

Analogy · busy secretary

منشی یک مطب شلوغ

تلفن‌ها پشت سر هم میاد. منشی سریع در دفترچه یادداشت می‌کنه (Memtable) و یک رونوشت هم نگه می‌داره (WAL). دفترچه که پر شد، مرتب‌شده‌اش رو بایگانی می‌کنه (SSTable). آخر هفته پرونده‌ها رو ادغام می‌کنه و نسخه‌های قدیمی رو دور می‌ریزه (Compaction).

کلید طلایی: هیچ آپدیت درجایی نداریم. همهٔ نوشتن‌ها ترتیبی (append) است، پس نوشتن خیلی سریعه.
۱. نوشتن ← به انتهای WAL روی دیسک اضافه می‌شه (برای بازیابی بعد از crash) و در Memtable مرتب در حافظه قرار می‌گیره.
۲. Flush ← Memtable پر شد؟ یک‌جا و مرتب روی دیسک نوشته می‌شه: یک SSTable تغییرناپذیر.
۳. Compaction ← چند SSTable در پس‌زمینه ادغام می‌شن؛ نسخه‌های قدیمی و حذف‌شده‌ها (tombstone) پاک می‌شن.
۴. خواندن ← اول Memtable، بعد SSTableها از جدید به قدیم. Bloom Filter هر SSTable می‌گه «قطعاً اینجا نیست» تا بی‌خودی خونده نشه.

import numpy as np, pandas as pd n = 1_000_000 rng = np.random.default_rng(42) df = pd.DataFrame({ "id": np.arange(n), "city": rng.choice(["Tehran", "Shiraz", "Tabriz", "Mashhad", "Isfahan"], n), "amount": rng.integers(10_000, 5_000_000, n), "created_at": pd.Timestamp("2026-01-01") + pd.to_timedelta(rng.integers(0, 300*86400, n), unit="s"), }) df.to_csv("orders.csv", index=False) df.to_json("orders.jsonl", orient="records", lines=True, date_format="iso") df.to_parquet("orders.parquet", compression="zstd") -- then in DuckDB: SELECT city, SUM(amount) FROM 'orders.parquet' GROUP BY city; SELECT * FROM parquet_metadata('orders.parquet');

قدم‌ها

  1. حجم سه فایل رو مقایسه کنید.
  2. کوئری GROUP BY رو روی CSV و Parquet با DuckDB زمان بگیرید.
  3. با parquet_metadata آمار min/max هر Row Group رو ببینید.
  4. داده رو بر اساس city مرتب کنید، دوباره بنویسید و فیلتر city='Shiraz' رو مقایسه کنید.
